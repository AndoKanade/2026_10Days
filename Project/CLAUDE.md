# 10daysJam「つなぐ」 開発ドキュメント

最終更新: 2026-08-31

---

## 1. プロジェクト概要

| 項目 | 内容 |
| --- | --- |
| 企画 | 10daysJam（テーマ：つなぐ） |
| 制作期間 | 10日（ゼロから制作） |
| ジャンル | 落ちものパズル |
| 言語・API | C++ / DirectX 12 |
| 開発環境 | Visual Studio 2026 |

配線が描かれたブロックを落として積み、下の電源から左右のゴールまで電気を通すと、通電したマスがまとめて消えるパズルゲーム。テーマ「つなぐ」が配線を繋ぐというルールそのものになっている。

---

## 2. ゲーム仕様

### 2.1 コアループ

1. 上からランダムなブロックが落ちてくる
2. プレイヤーが移動・回転させて配置する
3. 下の電源から左右のゴールまで配線が繋がると通電する
4. 通電したマスがすべて消える
5. 上のマスが落下し、再び通電すれば連鎖する
6. 天井に到達したらゲームオーバー

### 2.2 盤面

- 初期サイズは 10x10。開発しながら調整する。
- 電源は最下段の全マス。
- ゴールは左右の壁。
- 盤面幅は難易度に直結する。横断が難しすぎて消えない場合は幅を縮めて対応する。

### 2.3 ブロック

- 初期実装は L字（3マス）と T字（3マス）の2種類。仕組みが完成してから種類を追加する。
- ブロックの形そのものが配線の形になる。L字ブロックには L字に配線が通っている。
- 回転すると配線も一緒に回る。形と配線は常に一致する。
- 配線パターンは形ごとに固定とし、ランダムな割り当てはしない。

### 2.4 データ構造

- 各マスは上下左右の4bitで端子の有無を持つ。
- 隣接する2マスが繋がる条件は、互いに向き合う辺のbitが両方立っていること。
- 電源は最下段のマスの下辺bitが立っているとみなす。
- ゴールは左右端のマスの外側辺のbitが立っているとみなす。
- 各マスは元ブロックIDを持つ。最強マスの判定に使用する。

### 2.5 通電判定

- 最下段（電源）から幅優先探索で、繋がっているマスを塗る。
- ゴールに到達したら通電成立とする。
- 通電したマスはすべて消える。経路を1本に絞らず、枝分かれもループも含めて全部消す。
- 10x10なら毎フレーム実行しても負荷は問題ない。

### 2.6 通電の可視化

- 通電していない配線は暗い線で描画する。
- 電源から届いている配線は光らせる。
- 常時表示とし、ブロックを操作している最中もリアルタイムで反映する。「あと1マスで届く」がプレイヤーに見えることが重要。

### 2.7 消去と落下

処理の順序は以下の通り。

```
着地
 → 通電判定
 → 消去
 → 最強マス変換（落下前に判定する）
 → 落下（マス単位）
 → 再判定
 → 通電がなくなるまでループ
```

- 落下はマス単位で行い、ブロックの形は保持しない。連鎖が発生しうるのはこの方式のみ。
- この一連の処理中はプレイヤー入力と次ブロックの出現を止める。処理中フラグで制御する。
- 各段階に 0.2 〜 0.3 秒程度の間を入れ、連鎖が目で追えるようにする。

### 2.8 最強マス

- 全方向に端子を持つマス。
- 変換条件は、消去後に同じ元ブロックIDのマスが盤面に1マスだけ残ったとき。
- 判定は必ず落下前に行う。落下後だと別ブロックの断片が隣接し、正しく数えられなくなる。
- 最強マスは元ブロックIDを持たないため、以降の変換対象外とする。

### 2.9 スコア

通電したマス数に応じて加点する。線形にはしない。線形だと短い経路を何度も消すのが最適解になり、長く繋ぐ動機が消えるため。

| 通電マス数 | 倍率（仮） |
| --- | --- |
| 3〜5 | 1倍 |
| 6〜9 | 2倍 |
| 10〜14 | 4倍 |
| 15以上 | 8倍 |

連鎖にも別途倍率をかけ、狙いどころを2種類作る。

### 2.10 操作

- 左右移動
- 回転
- 下キーで加速
- 一気に落とす操作（任意）
- 着地から固定までの猶予を 0.5 秒程度設ける。ゼロだと手触りが固くなる。
- 回転が壁や既存ブロックと重なる場合は、まず回転を拒否する方式で実装する。余裕があれば押し戻して回す方式に変更する。

### 2.11 ゲームオーバー

- 天井到達で成立とする。
- 天井に迫ったら盤面の縁を点滅させるなどの警告を入れる。

### 2.12 難易度カーブ

- 落下速度の上昇は控えめにする。速すぎると通電を組み立てる時間が消え、別のゲームになる。
- 余裕があれば、一定時間ごとに下から1行せり上がる方式を検討する。思考時間を奪わずに圧力をかけられる。

## 3. 状態機械

即時処理で書かず、以下を明示的な状態として持つ。後からアニメーションを載せる方針は破綻しやすいため、最初から状態として組む。

- 操作中
- 着地判定
- 通電判定
- 消去演出中
- 最強マス変換
- 落下中
- 再判定
- ゲームオーバー

## 4. 開発ロードマップ

**最重要方針：5日目までにタイトルからリザルトまで通しで遊べる状態を作る。**
中身が薄くてもよい。ここが通っていれば残り5日をすべて改善に使える。逆にここが遅れると、演出と調整が丸ごと消える。

### Day 1：盤面とブロックの落下

- 定数ファイルを作る（盤面幅・高さ・落下間隔・固定猶予）
- 盤面の2次元配列を用意する
- マスのデータ構造を定義する（4bit端子と元ブロックID）
- ブロック定義（L字・T字）と4回転分の端子データを作る
- ブロックの落下・左右移動・回転を実装する
- 壁と既存ブロックとの衝突判定を実装する（回転は重なったら拒否）
- 着地して盤面に固定される処理を実装する
- ネクスト表示（1〜2個）を実装する
- 盤面幅を6と10で切り替えられるようにしておく

到達点：ブロックが落ちて積める。

### Day 2：配線の描画と通電判定

- 各マスの配線を描画する（形と配線が一致していることを目視確認）
- 最下段から幅優先探索で通電マスを塗る処理を実装する
- 左右の壁への到達判定を実装する
- 通電中の配線を光らせる（常時表示、リアルタイム更新）
- 通電していない配線は暗く表示する

到達点：積むと配線が光り、繋がったのが見える。

### Day 3：消去と最強マス

- 通電成立時に通電マスをすべて消す
- 消去直後、同じ元ブロックIDが1マスだけ残っていたら最強マスに変換する
- 最強マスの描画を実装する
- 最強マスは元ブロックIDを持たないようにする
- マス単位の落下処理を実装する

到達点：繋ぐと消える。ゲームとして成立する最小形。

### Day 4：連鎖と状態機械

- 状態機械に整理する
- 処理中フラグで入力と次ブロック出現を停止する
- 落下後の再判定ループを実装する（通電がなくなるまで）
- 各段階に 0.2 〜 0.3 秒の間を入れる
- 連鎖が目で追えることを確認する

到達点：連鎖が起きて、見て分かる。

### Day 5：ゲームとして通す

- スコア計算（通電マス数に応じた倍率テーブル）
- 連鎖倍率
- スコア表示
- ゲームオーバー判定（天井到達）
- タイトル画面
- リザルト画面
- タイトルへの復帰とリスタート

**マイルストーン：ここで通しで遊べること。**

### Day 6：テストと難易度調整

- 自分以外の人に触ってもらう（落ちものは自分では難易度が測れない）
- 盤面サイズを確定させる
- 消えない場合は幅を縮める。簡単すぎる場合はゴールに高さ制限を入れる
- 落下速度と固定猶予を調整する
- 最強マスの出現頻度が過剰でないか確認する
- 必要なら I字ブロックを追加する

### Day 7：演出

- 通電が経路を走るアニメーション（最優先。これがないと作業ゲーに見える）
- 消去エフェクト
- 連鎖時の表示
- 天井接近時の警告（縁の点滅など）
- ヒットストップや画面揺れ

### Day 8：音とUI

- SE（設置・回転・通電・消去・連鎖・ゲームオーバー）
- BGM
- UIの整理
- タイトルとリザルトの体裁を整える

### Day 9：調整

- 通しプレイを繰り返す
- 数値の最終調整
- バグ修正
- 余裕があればブロック種類を追加する

### Day 10：予備と提出

- ビルド確認
- 提出作業
- 説明文・スクリーンショットの用意

## 8. つまずきやすい箇所

| 箇所 | 内容 |
| --- | --- |
| 最強マス判定 | 落下前に判定しないと、別ブロックの断片が隣接して正しく数えられなくなる |
| 連鎖処理 | 入力を止めないと、処理中に次ブロックが降ってきて盤面が壊れる |
| 演出の後付け | 状態機械にせず即時処理で書くと、後からアニメーションを載せられない |
| 盤面幅 | 横断が難しすぎて消えないゲームになりやすい。Day 1から切り替えられるようにしておく |
| 通電の可視化 | ここを削ると、ただ端子を合わせるだけの作業になる |

## 10. 権利上の注意

テトロミノなどの形状自体、および落ちものパズルというルールに著作権はないが、以下は避ける。

- 「テトリス」「TETRIS」という名称
- 各ピースの固有配色（I=水色、O=黄色、T=紫、S=緑、Z=赤、J=青、L=オレンジ）
- 特徴的なロゴ、フォント、BGM
- 「テトリス風」といった宣伝文句

本作は端子の視認性で配色を決めるため、実質的に問題は起きにくい。なお、これは一般的な情報であり法的助言ではない。

## 11. 開発ルール

### 11.1 コーディング規約

- **命名規則・インデント**：一般的な C++ の規約に準拠すること。
- **コメントアウト**：処理の意図や内容をなるべく細かく具体的に記述すること。

### 11.2 実装時の禁止事項

- マジックナンバーの使用を禁止する。必ず定数（constexpr 等）を使用すること。
- 無駄な処理を何度も繰り返すような、非効率なコーディングをしないこと。

### 11.3 AIへの指示（厳守事項）

- 回答は短く簡潔にすること。
- 聞かれたこと以外の余計なコードを追加しないこと。
- コードの順番を勝手に変更しないこと。
- 変更箇所にはわかりやすい目印をつけること（ただし特殊な記号は使用しない）。
- コメントアウトに不自然な記号を使用しないこと。
- 提示されたコードを省略して返すのは禁止。
- 「整理して」と指示された場合は、処理内容は一切変更せず、不要なコメントの削除・わかりやすいコメントの追加・インデントの改善のみ行うこと（見やすさのための順番変更は許可する）。
